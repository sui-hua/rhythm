# Rhythm 移动端原生迁移设计

## 1. 背景

`Rhythm` 当前是基于 `Vue 3 + Vite + Tailwind CSS + Supabase` 的 Web 应用，核心能力围绕 `Day / Timeline`、`Direction`、`Habits`、`Summary` 展开。

现有项目已经为部分页面做过移动端响应式适配，但整体仍然是 Web 产品形态，主要问题包括：

- 交互模型以桌面布局为主，尤其是 `Day` 页仍依赖双栏结构与桌面弹窗
- 移动端体验受限于 Web 容器，不适合长期作为原生 App 主线
- 核心日执行流具备高频、强提醒、强手势潜力，更适合原生实现

本设计的目标不是把现有 Web 页面直接封装成 App，而是为移动端建立一个独立的原生产品形态，并以 `Day / Timeline` 作为第一阶段切入点。

## 2. 目标与非目标

### 2.1 目标

- 在 `/Users/sifan1/Documents/project/日程/rhythm-mobile` 建立独立的移动端项目
- 采用长期原生体验优先的技术路线，而不是 Web 壳方案
- 第一阶段只聚焦 `Day / Timeline` 的 MVP，确保用户可以在手机上完成每日执行闭环
- 继续复用现有 `Supabase` 后端、认证体系和任务数据模型
- 为后续接入 `Habits`、`Direction`、`Summary` 预留清晰演进路径

### 2.2 非目标

- 不在第一阶段迁移 `Month / Year / Summary / Direction / Habits` 页面
- 不追求第一版与 Web 功能完全对齐
- 不在第一阶段引入额外 BFF/API 层
- 不为了代码共享而强制重构现有 Web UI 层

## 3. 设计结论

### 3.1 技术路线

移动端采用独立的 `Expo + React Native + TypeScript` 技术栈，作为与 Web 并行维护的原生 App。

推荐组合：

- `Expo`
- `React Native`
- `TypeScript`
- `Expo Router`
- `TanStack Query`
- `Zustand`
- `Supabase`

不选 `Capacitor + Vue` 的原因：

- 与“长期原生体验优先”的目标冲突
- `Day / Timeline` 存在明显的原生手势、动画、通知场景
- 后续越做越深时，Web 壳的交互和性能限制会更明显

不选第一阶段自建 BFF 的原因：

- 会增加 MVP 启动成本
- 当前更需要先验证移动端日执行流的产品形态
- 现有 Supabase 已能支撑首版登录与任务读写

### 3.2 产品切入点

第一阶段只做 `Day / Timeline`，并且只做到可上线 MVP，而不是完整复刻 Web。

MVP 的上线标准是：

- 可以登录
- 可以查看当天任务
- 可以新增任务
- 可以编辑任务
- 可以删除任务
- 可以切换完成状态
- 可以收到基础本地提醒

## 4. 移动端信息架构

### 4.1 总体原则

移动端不复用 Web 的双栏结构，而是重构为单列主流程，突出“今天要做什么”和“如何快速完成”。

设计原则：

- 单手可操作
- 单列主视图
- 高频动作前置
- 次级能力收进抽屉或折叠区
- 编辑统一走底部 Sheet

### 4.2 Day 首页结构

建议页面结构如下：

1. 顶部日期区
2. 今日执行列表
3. 未安排任务区域
4. 底部新增入口

详细说明：

- 顶部日期区：展示当前日期、`今天` 快捷回跳、前一天/后一天切换
- 今日执行列表：按时间排序的任务卡片列表，是页面主体
- 未安排任务区域：承接没有开始时间的任务，避免污染主时间轴
- 底部新增入口：固定 FAB 或底部主按钮，快速新建任务

### 4.3 交互替换策略

以下 Web 交互在移动端不直接保留：

- 左侧 `Sidebar`
- 桌面弹窗式新增/编辑
- 多面板并行浏览
- 复杂拖拽排程
- 以“页面容器”而非“任务流”驱动的布局方式

移动端替换为：

- 单列滚动列表
- 底部 Sheet 编辑
- 折叠区或分段切换承接次级信息
- 轻量手势和点击操作优先

## 6. MVP 范围

### 6.1 首版页面

第一版包含以下 4 个页面/界面单元：

1. 登录页
2. Day 首页
3. 任务编辑 Sheet
4. 未安排任务区

### 6.2 首版能力

#### 登录页

- 支持现有 Supabase 认证流程
- 登录成功后默认进入“今天”

#### Day 首页

- 默认打开当天日期
- 支持切换昨天、今天、明天
- 按开始时间展示任务
- 任务卡片展示最小必要信息：
  - 标题
  - 开始时间 / 结束时间
  - 完成状态
  - 备注摘要（可选）

#### 任务编辑 Sheet

字段控制为最小集合：

- 标题
- 开始时间
- 结束时间
- 备注
- 完成状态

支持：

- 新建
- 编辑
- 删除

#### 未安排任务区

- 单独显示无开始时间的任务
- 不与主时间序列混排
- 可直接点入编辑或补充时间

#### 本地提醒

- 首版只做基础提醒
- 进入 App 后请求通知权限
- 为有时间的任务注册到点提醒

### 6.3 首版明确不做

- `daily_plan` 完整接入
- `habit` 完整接入
- 番茄钟
- 日报弹窗
- 自动顺延任务
- 月/年/总结页面
- 拖拽排程
- 复杂筛选、统计面板、多层联动

## 7. 数据与领域边界

### 7.1 后端复用策略

移动端首版继续复用现有：

- `Supabase` 项目
- 用户认证
- 任务表结构
- 行级权限控制

首版以 `task` 为唯一核心实体，不把 `daily_plan` 与 `habit` 的复杂聚合逻辑带入 MVP。

### 7.2 与现有 Web 的共享策略

不共享的部分：

- 页面组件
- 交互层
- 布局层
- Web 专属 composables

建议未来可共享的部分：

- 任务领域模型
- 时间排序规则
- 时间格式化逻辑
- 表单校验规则
- 日期解析与边界判断

结论是：

- 第一阶段不为了“共享”而重构 Web
- 先完成移动端 MVP
- 当移动端产品形态稳定后，再将纯函数级别的规则抽到公共 domain 层

## 8. 建议工程结构

移动端项目目录建议如下：

```text
rhythm-mobile/
  app/
  features/
    auth/
    day/
  services/
    supabase/
    notifications/
  domain/
    tasks/
  shared/
    ui/
    utils/
```

各层职责：

- `app/`：路由与页面入口
- `features/auth/`：登录流程、会话恢复
- `features/day/`：Day 页面、任务卡片、编辑 Sheet、日期切换
- `services/supabase/`：Supabase 客户端、任务查询、任务写入、认证适配
- `services/notifications/`：通知权限、调度、取消与重建
- `domain/tasks/`：任务模型、排序、时间转换、校验
- `shared/ui/`：通用按钮、输入框、Sheet、空状态组件

## 9. 状态管理策略

推荐分层如下：

- 服务端数据：`TanStack Query`
- 本地 UI 状态：`Zustand`

原因：

- `Day` 页存在列表拉取、缓存、刷新、局部更新需求
- 任务的新增/编辑/完成切换适合通过 Query 做缓存管理和失效控制
- Sheet 开关、局部表单状态、选中任务等更适合轻量本地 store

不建议第一阶段大量使用全局 store 承担服务端数据缓存，否则会过早把页面状态与后端数据耦合在一起。

## 10. Day 页交互模型

### 9.1 任务分组

首版任务按两组展示：

- 有时间的任务：进入主时间列表
- 无时间的任务：进入“未安排任务”区域

### 9.2 任务主操作

每个任务卡片支持以下核心动作：

- 点击打开编辑 Sheet
- 点击完成按钮切换状态
- 从未安排任务补充时间

首版不加入复杂手势作为核心依赖，避免早期在交互上引入不可控复杂度。

### 9.3 时间线呈现方式

虽然模块名仍然是 `Day / Timeline`，但首版移动端不需要强行复刻 Web 中“24 小时视觉时间轴”的形式。

建议首版采用“按时间排序的时间列表”，保留时间语义，而不执着于完整纵轴刻度。这样可以：

- 降低首版布局复杂度
- 提高小屏信息密度
- 让用户更快进入执行状态

后续若验证用户需要更强的时间轴感知，再演进为更明显的原生时间线视觉结构。

## 11. 通知能力设计

首版只实现基础本地提醒，不做复杂通知编排。

能力边界：

- 请求通知权限
- 为有明确开始时间的任务注册本地通知
- 当任务被删除或修改时间时，取消并重建对应通知

首版不做：

- 多阶段提醒
- 番茄钟通知
- 后台自动续期逻辑
- 基于 `daily_plan` / `habit` 的复合提醒

## 13. 风险与约束

### 12.1 数据模型风险

现有 Web 的 `Day` 页通过 `useDayData` 与 `buildDayExecutionItems` 聚合 `task / daily_plan / habit` 三类数据。移动端首版若强行完整继承，会显著提高复杂度，因此必须接受“首版只做 task 主链路”的范围裁剪。

### 12.2 通知一致性风险

移动端本地通知一旦接入，就必须明确通知与任务更新之间的同步策略，否则容易出现提醒过期、重复提醒或任务删除后仍被提醒的问题。

### 12.3 双端分栈成本

移动端与 Web 分栈意味着：

- UI 实现两套维护
- 交互演进需要分别考虑
- 需要更早建立清晰的领域边界

这是一项明确接受的成本，用来换取长期更好的原生体验。

## 14. 后续演进方向

在 MVP 稳定之后，建议按以下顺序扩展：

1. 补齐 `daily_plan` 接入
2. 补齐 `habit` 接入
3. 增加更强的时间轴视觉表达
4. 加入番茄钟
5. 加入日报与顺延逻辑
6. 评估是否抽离共享 domain 层

## 15. 最终结论

本项目的移动端迁移，应采用“独立原生 App + 复用现有 Supabase 后端”的路线，在 `/Users/sifan1/Documents/project/日程/rhythm-mobile` 新建 `Expo + React Native + TypeScript` 项目。

第一阶段只做 `Day / Timeline` 的可上线 MVP，并且只保留用户每天真正会使用的最小闭环：登录、查看当天任务、新增、编辑、删除、完成切换、基础提醒。

通过这种方式，可以在不被现有 Web 布局拖累的前提下，为 `Rhythm` 建立移动端长期演进的正确基础。
