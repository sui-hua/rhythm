# 代码规范

> 适用范围：`apps/api`、`apps/web-next`、`apps/mobile`。`apps/web`（Vue 端）暂不强制，但它直连 Supabase 的写法不在本规范推荐范围内。
>
> 本文只约定「文件怎么分、每层能干什么」。格式类约定沿用各 app 自己的配置（`apps/api/.prettierrc` + `oxlint.json`），不做跨端统一。

---

## 0. 一句话总则

**一个业务概念 = 后端 4 个文件 + 前端 3 层。**

- 后端：`module` / `controller` / `service` / `dto`，四个文件各管一件事，**prisma 只出现在 service 里**。
- 前端：视图层 / 数据层 / 接口层，**`snake_case` 不许越过接口层**。

判断代码该放哪，只问一句：**这段逻辑，换掉数据库或换掉 UI 之后还成立吗？** 成立的是业务（service / domain），不成立的是适配（controller / 接口层）。

## 1. 后端（apps/api）

### 1.1 模块目录固定四件套

以 `task` 为例：

```
apps/api/src/tasks/
├── tasks.module.ts        # 装配：controller + service
├── tasks.controller.ts    # 路由：URL、方法、参数绑定
├── tasks.service.ts       # 业务 + 数据访问（this.prisma）
└── dto/
    └── task.dto.ts        # 入参校验与类型
```

- 目录名用**复数资源名**（`tasks`、`habits`、`summaries`），文件名用**单数资源名 + 角色后缀**。
- 文件名 kebab-case，类名 PascalCase（`tasks.controller.ts` → `TasksController`）。
- DTO 统一放 `dto/` 子目录，一个模块一个 DTO 文件；一个模块下有多个子资源时才拆（如 `direction/dto/direction.dto.ts` 涵盖 goal / month / day / category）。
- 一个模块下资源超一个时，按资源拆多组 controller + service，但仍共用**一个 module 目录**（见 `direction/`：4 个 controller + 4 个 service + 1 个 module）。

### 1.2 各层职责与红线

| 文件 | 只做 | 明令禁止 |
|------|------|----------|
| `*.controller.ts` | 声明路由与方法、绑定 `@Body/@Query/@Param/@CurrentUserId`、调 service、直接 `return` | 写 `this.prisma`、写 if/else 业务判断、手动 `new Date()`、`try/catch` 后自己拼响应、import `Prisma` 类型 |
| `*.service.ts` | 业务规则、`dto → Prisma data` 转换、所有数据库读写、抛 `HttpException` | 出现 `@Req/@Res/Request/Response`、`setGlobalPrefix` 之类的 HTTP 细节、返回未序列化的 `Date` |
| `dto/*.dto.ts` | `class-validator` 装饰器 + 类型声明 | 查库、调用 service、做业务计算 |
| `*.module.ts` | `controllers` / `providers` 装配 | 写逻辑 |

**具体约定：**

1. **service 方法签名第一个参数永远是 `userId`。**
   ```ts
   list(userId: string, query: ListTaskQueryDto)
   update(userId: string, id: string, dto: UpdateTaskDto)
   ```
   线上库的 `user_id` 原本靠 Supabase RLS 兜底，自托管后必须在应用层显式过滤，**每个查询的 `where` 都要带 `user_id`**。

2. **改 / 删之前先校验归属。** 复用 `getById`（它内部已带 `user_id`），查不到抛 `NotFoundException`：
   ```ts
   async update(userId: string, id: string, dto: UpdateTaskDto) {
     await this.getById(userId, id); // 越权保护
     return this.prisma.task.update({ where: { id }, data: toUpdateData(dto) });
   }
   ```

3. **入参转换用模块内的私有函数**，命名固定 `toCreateData` / `toUpdateData`，写在 service 文件顶部，不挂到类上：
   - 只转换、不查库；
   - `UpdateXxxDto` 必须逐字段判 `!== undefined`，**不能用 `?? ` 兜底**，否则「不传」和「传 null」会混淆。

4. **出参必须序列化。** Prisma 的 `date` / `time` 列是 `Date` 对象，直接返回会变成 `2026-10-29T00:00:00.000Z`，与前端历史约定不一致。带 `Date` 字段的返回一律过 `serializeRow` / `serializeRows`（`common/db-serializers.ts`）：
   - `date` 列 → `YYYY-MM-DD`
   - `time` 列 → `HH:mm:ss`
   - `timestamptz` → ISO 字符串

5. **错误只用 Nest 内置异常**（`NotFoundException` / `BadRequestException` / `ForbiddenException`），文案面向用户、中文、不带技术细节。不要自定义错误码体系，也不要返回 `{ code, msg }` 包装。

6. **ESM 的 import 必须带 `.js` 后缀**（`import { PrismaService } from '../prisma/prisma.service.js'`），漏了会在 `node dist/main` 时炸。

### 1.3 方法命名固定词汇

| 场景 | 命名 |
|------|------|
| 列表 | `list`（带筛选）、`listInbox` / `listByKind`（特定子集） |
| 详情 | `getById` |
| 创建 / 更新 / 删除 | `create` / `update` / `remove` |
| 特殊动作 | 动词短语：`toggle`、`batchUpsert`、`carryOver` |

### 1.4 模块之间

- service 之间**允许**注入复用（`DirectionModule` 里 goals ↔ goal-months），但**禁止循环依赖**；一旦要互相注入，说明该抽第三层或把公共逻辑下移到 `common/`。
- 跨模块共用的纯函数（日期区间、序列化、用户解析）统一放 `src/common/`，并在 `common/index.ts` 里 re-export。
- `x-user-id` 的读取只允许出现在 `common/current-user-id.decorator.ts`，业务代码一律用 `@CurrentUserId()`，将来换 JWT 只改一处。

## 2. 前端（apps/web-next + apps/mobile）

前端是**三层 + 一个可选纯逻辑区**，不是四层。

| 层 | mobile | web-next | 只做 | 明令禁止 |
|----|--------|----------|------|----------|
| **视图层** | `app/(app)/*.tsx`<br>`src/features/*/screens/*.tsx`<br>`src/features/*/components/*.tsx` | `src/app/*/page.tsx`<br>`src/components/*` | JSX、布局、样式、把用户操作转成回调 | `fetch`、拼 URL、写 `snake_case` 字段名、做字段映射 |
| **数据层** | `src/features/*/hooks/use*.ts` | 页面内 hook + `src/lib/use-async-data.ts` | `useQuery` / `useMutation`、`queryKey`、成功后失效缓存、把接口数据整理成页面要的形状 | 拼 URL、认识后端字段名、直接操作 DOM / RN 组件 |
| **接口层** | `src/services/api/*.ts` | `src/lib/api/*.ts` | URL、method、body、**snake_case ↔ camelCase 映射**、错误转义 | 业务判断、React state / hooks、组件相关逻辑 |
| **纯逻辑区**（可选，不算层） | `src/domain/**` | `src/lib/*.ts`（`date.ts`、`goal-progress.ts`…） | 纯函数：日期、进度、分组、表单校验、排序。输入输出都是领域模型 | `fetch`、hooks、任何副作用 |

### 2.1 三条硬规则

1. **`snake_case` 不许越过接口层。** 后端的 `start_time` 在接口层就被映射成 `startAt`，组件和 domain 里永远见不到下划线字段名。
   ```ts
   // services/api/tasks.ts —— 唯一认识后端字段的地方
   type TaskRow = { id: string; title: string; start_time: string | null; end_time: string | null }
   function mapRow(row: TaskRow): TaskRecord {
     return { id: row.id, title: row.title, startAt: row.start_time, endAt: row.end_time }
   }
   ```

2. **接口层只导出「动词 + 资源」的函数，且返回领域模型，不返回后端 row。**
   ```ts
   export async function listTasksForDate(date: Date): Promise<TaskRecord[]>
   export async function createTask(input: TaskFormInput): Promise<TaskRecord>
   ```
   不许导出 `get('/tasks')` 这种通用请求器给页面用——`apiRequest` 只在接口层内部可见。

3. **错误只由接口层转一次。** `client.ts` 把非 2xx / 超时 / 连不上统一成 `ApiError`，页面和 hook 只读 `error.message`，**不再二次包装、不再拼文案**。

### 2.2 缓存与命名

- `queryKey` 用 `[资源, 维度]` 数组：`['day-tasks', dateKey]`、`['day-daily-plans', dateKey]`、`['habits']`。
- 写操作成功后**只失效相关 key**，不 `invalidateQueries()` 全量刷。
- 新增资源时，`queryKey` 的第一个元素统一用 **kebab-case 资源名**，避免同一个接口出现两种 key。

### 2.3 两端对齐

- 同一个后端接口，mobile 和 web-next 各有一份接口层文件，**映射规则必须一致**（字段名、`null → ''` 之类的兜底都要一致）。改动其中一份时，另一份同步改。
- 领域模型类型（`TaskRecord` / `HabitRecord` …）两端保持同名字段，为将来抽 `packages/shared` 做准备。目前不抽包，但**不允许两端字段名不同**。
- `web-next/src/lib/api/index.ts` 目前是单文件聚合，**超过约 400 行就按资源拆**成 `lib/api/tasks.ts` 等，与 mobile 的目录形状对齐。

## 3. 跨端契约

| 类型 | 后端产出 | 前端形态 |
|------|----------|----------|
| `date` 列 | `"2026-10-29"` | 字符串日期 key，用 `toDateKey` 比较 |
| `time` 列 | `"09:00:00"` | 字符串，展示前格式化 |
| 时间戳 | ISO 字符串 | 需要 Date 时在纯逻辑区转 |
| 用户标识 | `x-user-id` 请求头 | mobile 从 session 取，web-next 用 `DEV_USER_ID` |

**接口字段格式一旦定下不随意改。** 要改就必须三端同批改，否则会出现「web 正常、mobile 显示差一天」这类问题时无法定位。

## 4. 提交前自查

**后端**

- [ ] `controller` 里没有 `prisma`、没有 `Prisma` 类型 import
- [ ] 每个查询 `where` 都带 `user_id`
- [ ] 改 / 删前调用了 `getById` 做归属校验
- [ ] 返回体带 `Date` 字段的已过 `serializeRow(s)`
- [ ] 相对 import 带 `.js` 后缀；`pnpm api:build` 通过

**前端**

- [ ] 组件 / domain 里搜不到 `_[a-z]` 形式的后端字段
- [ ] 请求只出现在接口层文件里
- [ ] 接口层返回领域模型，不是 row
- [ ] 新增写操作带上了精准的 `invalidateQueries`
- [ ] `pnpm mobile:typecheck` / `pnpm next:typecheck` 通过

## 5. 存量代码怎么办

当前 `tasks`、`habits`、`summaries`、`daily-reports`、`direction` 五个模块已基本符合本文结构（controller 薄、service 承载业务与 prisma 访问），**不需要专门重构**。差异只在这些点，改到哪个模块顺手对齐即可：

| 待对齐项 | 现状 | 目标 |
|----------|------|------|
| `toCreateData` / `toUpdateData` | 已用，命名一致 | 保持 |
| service 是否只返回序列化结果 | 部分模块返回 raw row，由 controller/serialize 兜 | 统一在 service 末尾 `serializeRow` |
| DTO 文件粒度 | 每模块一个 | 保持 |
| 前端 `web-next/src/lib/api/index.ts` | 单文件 | 超 400 行按资源拆 |

**新代码一律按本文执行**，不再讨价还价；老代码不主动动，避免为了规范引入回归。

## 6. 分层 skill（AI 辅助）

每一层有一份独立的操作手册，放在 `.workbuddy/skills/`，按文件类型自动命中。写代码前先看对应那份，里面有可直接抄的骨架和该层的红线清单。

| Skill | 命中场景 | 对应本文 |
|-------|----------|----------|
| `api-controller` | 改 `*.controller.ts`、加路由、调接口路径 | §1.2 |
| `api-service` | 改 `*.service.ts`、写查询、加归属校验 | §1.2 |
| `api-dto` | 改 `dto/*.dto.ts`、加校验、字段被静默丢弃 | §1.2 |
| `api-module` | 新增模块、接口 404、`Nest can't resolve dependencies` | §1.2 / §1.4 |
| `web-view` | 改 `screens/`、`app/*/page.tsx`、拆组件 | §2 |
| `web-data-hooks` | 改 `features/*/hooks/`、`queryKey`、缓存失效 | §2.1 / §2.2 |
| `web-api-client` | 改 `services/api/`、`lib/api/`、字段对不上 | §2.1 |
| `web-domain` | 改 `domain/`、`lib/*.ts`、日期与进度计算 | §2 |

> 注：`.gitignore` 目前整体忽略 `.workbuddy/`，这些 skill 仅存在于本地。若要让团队共享，需把规则改成 `.workbuddy/*` + `!.workbuddy/skills/`，同时保留 `.workbuddy/memory/` 被忽略。
